= Property Encryption
:test-skip: true

Property Encryption allows Neo4j properties to be encrypted and decrypted on the driver side.

Property values are encrypted and encoded into bytes. The resulting bytes contain the encrypted value together with the
metadata required to decrypt it. The application is responsible for storing these bytes in a representation supported by
Neo4j property types. To decrypt a value, the application retrieves the stored bytes and provides them to the driver.

The feature is designed to be easy to use, with an opinionated approach to encryption and decryption. All official Neo4j
drivers are expected to support the feature, enabling interoperability between drivers when they are configured to use
compatible encryption settings.

.Preview Feature
[IMPORTANT]
====
The preview feature is a new feature that is a candidate for a future GA status.
It enables users to try the feature out and maintainers to refine and update it.
The preview features are not considered to be experimental, temporary or unstable.
However, they may change more rapidly, without following the usual deprecation cycle.
Most preview features are expected to be granted the GA status unless some unexpected conditions arise.
====

[NOTE]
This feature is available from version 6.3.0 onwards.

[NOTE]
====
At present, all encryption and decryption is manual. As an official Neo4j Driver feature, Property Encryption enables:

* **Cross-driver and cross-version interoperability**: Consistent encryption and decryption of Neo4j Property values
  across drivers and supported driver versions, including consistent Additional Authenticated Data (AAD) handling. This
  enables a Neo4j Property encrypted by a driver in one language to be successfully decrypted by a driver in another
  language.
* **Standardized cryptography**: The cryptographic algorithms and parameters, including key sizes, initialization vector
  (IV) sizes, and authentication tag sizes, are defined by the feature and selected with FIPS requirements in mind.
  The driver is designed to function with a runtime that enforces a FIPS-compliant cryptographic provider.
* **Composable key management**: The envelope encryption design separates property encryption from key protection and
  allows different key encapsulation mechanisms to be integrated through a well-defined API. 
* **Standardized encrypted-value representation**: The driver defines how encrypted property values and the metadata
  required for their decryption are encoded, providing a common representation that can be stored using Neo4j-supported
  property types.
* **Server version agnostic**: Encryption and decryption are performed on the driver side, with encrypted values
  represented as bytes that can be stored as Neo4j Properties. This allows the feature to be used with any Neo4j server
  version supported by the driver, without requiring server upgrade.
====

While <<property-encryption-api>> includes a more detailed overview, the following two examples demonstrate the basic
usage of the API.

.Encryption example
[source, javascript]
----
const encryptedValue = await driver.encryption.encrypt({
    value: "Secret String", // <1>
    keyOptions: {alias: "key1"}, // <2>
    encryptionProfile: "profile1", // <3>
    aad: 123 // <4>
}) // <5>
----
<1> Any value which can be stored as a property in a Neo4j database can be encrypted by the driver
<2> The driver can handle multiple Data Encryption Keys for different data
<3> The driver can have multiple encryption configurations, each one defined by an encryption profile.
<4> Encryption is done with AES-GCM-256, which supports Additional Authenticated Data. 
<5> Produces an Int8Array, which the driver will send as a byteArray

.Decryption example
[source, javascript]
----
const decryptedValue = await driver.encryption.decrypt({
    ciphertext: result.records[0].get("x"),
    aad: 123
})
----

[#encryption-profile]
== Encryption profile

An encryption profile defines the settings and operating mode used by the driver when encrypting and decrypting values.

Each profile has a unique, user-defined name. The profile name is stored with encrypted values and allows drivers to
identify which profile must be used to decrypt a value.

Multiple profiles can be configured at the same time, providing each has a unique name.

[IMPORTANT]
When driver interoperability is required, users are expected to configure each driver with compatible profiles.

Profiles are configured at the driver level using a driver configuration option:

.Add profiles to driver configuration
[source, javascript]
----
const driver: Driver = neo4j.driver("neo4j://address", neo4j.auth.basic("user", "password"), {
    encryptionProfiles: [profile] // <1>
})
----

<1> Accepts one or multiple profiles.

`EncryptionProfile` is the base type for encryption profiles. At present, the driver provides one profile type:
`EnvelopeEncryptionProfile`. Additional profile types may be introduced in the future.

[#envelope-profile]
=== Envelope profile

`EnvelopeEncryptionProfile` enables envelope encryption of Neo4j properties.

Envelope encryption separates the encryption of the data from the protection of the key used to encrypt that data. The
key used to encrypt the data is sometimes referred to as a Data Encryption Key (DEK). Depending on the implementation,
the encryption key may be the DEK itself or it may be derived from the DEK.

The DEK must itself be protected. When a separate Key Encryption Key (KEK) is used to protect the DEK, the process is
commonly referred to as key wrapping. Alternatively, a Key Encapsulation Mechanism (KEM) can be used to protect or
establish the secret material associated with the DEK. In the latter case, the terminology and exact mechanism depend on
the KEM being used, such as MK-KEM.

The envelope profile setup requires two fundamental components. These are covered in separate sections, but are briefly
introduced here:

* <<key-encapsulation-service>> - responsible for generating, encapsulating, and decapsulating data encryption keys.
* <<encapsulated-key-record-repository>> - responsible for providing storage for encapsulated keys.

Property values are encrypted using the following:

* **Encryption Key** — AES-256
* **Encryption algorithm** — AES-GCM ("AES/GCM/NoPadding")
* **Initialization vector (IV)** — 12 bytes (96 bits)
* **Authentication tag** — 16 bytes (128 bits)
* **Additional authenticated data (AAD)** — optional

The `EnvelopePropertyEncryptionProfile` provides a builder for creating a profile instance.

.Create an envelope profile
[source, javascript]
----
new EnvelopeEncryptionProfile({
    name: "main", //name of the encryption profile, 
    encapsulationService: neo4j.localKeyEncapsulationService(masterkey), //the service responsible for generating, encapsulating and decapsulating Data Encryption Keys (DEKs). The driver provides an implementation that uses a local 256-bit masterkey
    keyRepository: new userImplementedKeyRepo() // The place to store encapsulated DEKs, must be implemented by the user, an example implementation is provided further down.
})
----

The builder has additional options that are introduced alongside the relevant concepts later in this manual.

[#key-encapsulation-service]
== Key Encapsulation Service

Key Encapsulation Service is responsible for generating, encapsulating, and decapsulating data encryption keys. It
generates a new data encryption key together with its encapsulation, and can later decapsulate the encapsulation to
recover the data encryption key when it is needed for encryption or decryption.

The key encapsulation mechanism is implementation-specific. It may use key wrapping, symmetric or asymmetric
cryptography, a key management service (KMS), or a post-quantum key encapsulation mechanism such as ML-KEM.

The service is represented by `KeyEncapsulationService` interface that has 2 primary methods:

* `encapsulate` - supplies a new AES-256 key and its encapsulation
* `decapsulate` - decapsulates an existing encapsulation to AES-256 key

.KeyEncapsulationService
[source, javascript]
----
/**
 * A service responsible for encapsulating and decapsulating keys.
 *
 * @see KeyEncapsulationOptions
 * @see KeyEncapsulationResult
 * @since 6.3.0
 * @experimental Part of the Client-Side Encrytion preview feature
 */
export interface KeyEncapsulationService {
  /**
   * Creates a new key, encapsulates it and returns the result.
   *
   * @param {KeyEncapsulationOptions} options the encapsulation options, depends on the implementation
   * @return {Promise<EncapsulationResult>} a promise that resolves to the encapsulation result
   */
  encapsulate: (options: KeyEncapsulationOptions) => Promise<EncapsulationResult>

  /**
   * Decapsulates encapsulated bytes.
   *
   * @param {Int8Array} encapsulation the encapsulated byte
   * @param {KeyEncapsulationOptions} metadata the key metadata
   * @return {Promise<Uint8Array>} a promise that resolves to the decapsulated key
   */
  decapsulate: (encapsulation: Int8Array, metadata: KeyEncapsulationOptions) => Promise<Uint8Array>
}
----

The interface can be implemented to integrate different key encapsulation mechanisms. The driver also provides several
implementations, described in the following sections.

=== Local

The local implementation uses a user-provided AES-256 `SecretKey` as a master key for encapsulating and decapsulating
data encryption keys.

The encapsulation uses AES-GCM (`"AES/GCM/NoPadding"`) with the provided master key. The resulting encapsulation
contains a 256-bit AES data encryption key protected by the master key, together with a 96-bit (12-byte) initialization
vector (IV) and a 128-bit (16-byte) authentication tag.

.Create a service instance
[source, javascript]
----
const encapsulationService = neo4j.localKeyEncapsulationService(masterkey);
----

[#encapsulated-key-record-repository]
== Encapsulated Key Record Repository

An Encapsulated Key Record Repository is a user-provided repository for storing encapsulated data keys and their
associated metadata.

Each encapsulated key record has a globally unique and immutable identifier.

[IMPORTANT]
====
The repository implementation is responsible for assigning globally unique and immutable key identifiers.
In addition, the repository is also responsible for enforcing alias uniqueness.
====

The repository is represented by `EncapsulatedKeyRecordRepository` interface that has 5 primary methods:

* `create` - creates a new key record
* `findById` - finds key by id
* `findByAlias` - finds key by alias
* `setAliasById` - sets key alias by id
* `deleteById` - deletes key by id

.EncapsulatedKeyRecordRepository
[source, javascript]
----
/**
 * A repository for {@link EncapsulatedKeyRecord} data.
 * An implementation of this must be provided to a {@link EncryptionProfile} so that the driver knows where to store and retreive encapsulated keys.
 *
 * @since 6.3.0
 * @experimental Part of the Client-Side Encrytion preview feature
 */
export interface EncapsulatedKeyRecordRepository {
  /**
   * Finds and returns an {@link EncapsulatedKeyRecord} by its id.
   *
   * @param {string} id the key id
   * @return {Promise<EncapsulatedKeyRecord>} a promise that resolves to the key or undefined if no key with the given id exists
   */
    findById: (id: string) => Promise<EncapsulatedKeyRecord>

  /**
   * Finds and returns an {@link EncapsulatedKeyRecord} by its alias.
   *
   * @param {string} alias the key alias
   * @return {Promise<EncapsulatedKeyRecord>} a promise that resolves to the key or undefined if no key with the given alias exists
   */
    findByAlias: (alias: string) => Promise<EncapsulatedKeyRecord>

  /**
   * Creates the encapsulation as a key and assigns it a globally unique id.
   *
   * The generated id MUST be globally unique and immutable. Implementations SHOULD use a mechanism designed to
   * generate globally unique identifiers, such as UUIDs.
   *
   * @param {string} alias the key alias
   * @param {Int8Array} encapsulation the key encapsulation
   * @param {Record<string, string>} metadata the key metadata
   * @return {Promise<EncapsulatedKeyRecord>} a promise that resolves to the created key
   */
    create: (alias: string, encapsulation: Int8Array, metadata: Record<string, string>) => Promise<EncapsulatedKeyRecord>

  /**
   * Sets the alias of an encapsulated key by id. 
   * The alias must not be used by another key and the implementation of this function should throw if it is.. 
   * To assign an alias currently used by another key, it must first be deleted from that key.
   * 
   * @param {string} id the key id
   * @param {string | undefined} alias the key alias, may be null or undefined to remove the alias
   * @return {Promise<void>} promise that resolves when the alias has been set
   */
    setAliasById: (id: string, alias: string | undefined) => Promise<void>

  /**
   * Deletes a key by id.
   *
   * @param {string} id the key id
   * @return {Promise<void>} promise that resolves when the key has been deleted
   */
    deleteById: (id: string) => Promise<void>
}
----

[NOTE]
An implementation of repository is supplied by the user.

An example of a typescript implementation using Cypher 5 is shown below.

.Sample Cypher 5 implementation
[source, typescript]
----
/**
 * A sample {@link EncapsulatedKeyRecordRepository} implementation using Cypher 5.
 */
class Neo4jEncapsulatedKeyRecordRepository implements EncapsulatedKeyRecordRepository {
    private static CONSTRAINTS = [
        `CYPHER 5
        CREATE CONSTRAINT key_id IF NOT EXISTS
        FOR (k:Key)
        REQUIRE k.id IS UNIQUE`,
        `CYPHER 5
        CREATE CONSTRAINT key_alias IF NOT EXISTS
        FOR (k:Key)
        REQUIRE k.alias IS UNIQUE`
    ];
    private static CREATE_QUERY =
            `CYPHER 5
    CREATE(key: Key {
        id: randomUUID(),
                alias: $alias,
                encapsulation: $encapsulation
            })-[:HAS_METADATA]->(metadata:KeyMetadata $metadata)
            RETURN key, metadata`;
    private static FIND_BY_ID_QUERY =
            `CYPHER 5
            MATCH (key:Key {id: $id})-[:HAS_METADATA]->(metadata:KeyMetadata)
            RETURN key, metadata
            LIMIT 1`;
    private static FIND_BY_ALIAS_QUERY = 
            `CYPHER 5
            MATCH (key:Key {alias: $alias})-[:HAS_METADATA]->(metadata:KeyMetadata)
            RETURN key, metadata
            LIMIT 1`;
    private static SET_ALIAS_BY_ID_QUERY =
            `CYPHER 5
            MATCH (key:Key {id: $id})
            SET key.alias = $alias`;
    private static DELETE_BY_ID_QUERY =
            `CYPHER 5
            MATCH (key:Key {id: $id})-[:HAS_METADATA]->(metadata:KeyMetadata)
            DETACH DELETE key, metadata`;


    private static resultTransformer = async (r: Result) => {
                    const record = (await r).records[0]
                    const result: EncapsulatedKeyRecord = {
                        encapsulation: () => record.get("key").properties.encapsulation,
                        id: () => record.get("key").properties.id,
                        alias: () => record.get("key").properties.alias,
                        metadata: () => record.get("metadata").properties
                    }
                    return result
                }
    
    private driver: Driver;
    private database: string

    constructor(driver: Driver, database: string) {
        this.driver = driver;
        this.database = database
    }

    public async createConstraints() {
        for (const constraint of Neo4jEncapsulatedKeyRecordRepository.CONSTRAINTS) {
            await this.driver.executeQuery(constraint, undefined, {database: this.database})
        }
    }

    public async findById(id: string): Promise<EncapsulatedKeyRecord> {
        var result = await this.driver.executeQuery(
            Neo4jEncapsulatedKeyRecordRepository.FIND_BY_ID_QUERY,
            {
                id
            },
            {
                database: this.database,
                resultTransformer: Neo4jEncapsulatedKeyRecordRepository.resultTransformer
            }
        )
        return result
    }

    public async findByAlias(alias: string): Promise<EncapsulatedKeyRecord> {
        var result = await this.driver.executeQuery(
            Neo4jEncapsulatedKeyRecordRepository.FIND_BY_ALIAS_QUERY,
            {
                alias
            },
            {
                database: this.database,
                resultTransformer: Neo4jEncapsulatedKeyRecordRepository.resultTransformer
            }
        )
        return result
    }

    public async create(alias: string, encapsulation: Int8Array, metadata: Record<string, string>): Promise<EncapsulatedKeyRecord> {
        var result = await this.driver.executeQuery(
            Neo4jEncapsulatedKeyRecordRepository.CREATE_QUERY,
            {
                alias,
                encapsulation,
                metadata
            },
            {
                database: this.database,
                resultTransformer: Neo4jEncapsulatedKeyRecordRepository.resultTransformer
            }
        )
        return result
    }
    
    public async setAliasById(id: string, alias: string | undefined): Promise<void> {
        await this.driver.executeQuery(
            Neo4jEncapsulatedKeyRecordRepository.SET_ALIAS_BY_ID_QUERY,
            {
                id,
                alias
            },
            {
                database: this.database
            }
        )
        return
    }

    public async deleteById(id: string): Promise<void> {
        await this.driver.executeQuery(
            Neo4jEncapsulatedKeyRecordRepository.DELETE_BY_ID_QUERY,
            {
                id
            },
            {
                database: this.database
            }
        )
        return
    }
}
----


[#property-encryption-api]
== Property Encryption API

The Property Encryption API is exposed through `EncryptionSerivce`, which is available directly from the `Driver`
object. This makes the API easy to access, particularly in existing applications where the driver object is already
available.

.Obtain PropertyEncryption
[source, javascript]
----
const encryptionService = driver.encryption;
----


=== EncapsulatedKeyManager

The <<envelope-profile>> requires data keys to exist before they can be used to encrypt or decrypt property values.

Creating a data key involves obtaining a new data encryption key and its encapsulation from the
<<key-encapsulation-service>> and creating the corresponding record in the <<encapsulated-key-record-repository>>.

To simplify these operations, `PropertyEncryption` provides an `EncapsulatedKeyManager` through
`EncryptionService#keyManager()` when a single profile is configured and `EncryptionService#keyManager(String)` when
multiple profiles are configured.

.Obtain key manager
[source, javascript]
----
const keyManager = encryptionService.keyManager("profile-name");
----

[NOTE]
====
A data key can be referenced by its globally unique identifier or, if assigned, by an alias. Both are *String* values.

The key identifier is immutable and globally unique, assigned by the key repository. The alias is a mutable,
application-level reference that can be reassigned to a different key over time.

Aliases allow applications to refer to keys using stable application-level names without having to reference the key's
identifier.
====

The key manager provides operations to create, find, and delete keys. It also provides operations to set and delete key
aliases. When <<caching>> is enabled, key management operations update the <<key-cache>> and <<key-alias-index>> as
necessary.

.Create a data key with an alias
[source, javascript]
----
const key = await keyManager.create("users-key");
----

The returned `EncapsulatedKey` has accessors for:

* **id** - the globally unique key identifier
* **alias** - the key alias if assigned

.Find key by alias
[source, javascript]
----
const key = await keyManager.findByAlias("users-key");
----

.Set alias by id
[source, javascript]
----
await keyManager.setAliasById(key.id(),"users-key");
----

.Delete alias by id
[source, javascript]
----
await keyManager.deleteAliasById(key.id());
----

.Delete key by id
[source, javascript]
----
await keyManager.deleteById(key.id());
----


=== encrypt

Property values can be encrypted using the asynchronous `encrypt` function, which takes a parameter object.

.Encrypt value
[source, javascript]
----
const encryptedValue = await driver.encryption.encrypt({
    value: "Secret String", // <1>
    keyOptions: {alias: "key1"}, // <2>
    encryptionProfile: "profile1", // <3>
    aad: "user1" // <4>
}) // <5>
----

<1> A mandatory parameter for providing the value to encrypt. This method supports all types listed in <<supported-types>>.
<2> A mandatory parameter for specifying encryption key to use. This is an alias version, but there is also `usingKeyId` variant.
<3> An optional parameter for specifying <<encryption-profile>> name. It is mandatory when multiple profiles are configured.
<4> An optional parameter for providing Additional Authenticated Data (AAD), which is described later in this section.
<5> Produces an Int8Array, which the driver will send as a byteArray

[IMPORTANT]
The encrypted value always references the encryption key identifier, which is expected to be immutable and globally
unique. This ensures that the identifier used by the encrypted value is stable, even when a key alias is used in the
encryption request.

Additional Authenticated Data (AAD) is optional, non-secret data that is authenticated together with the encrypted
value but is not itself encrypted. The same AAD must be provided during decryption. Otherwise, decryption fails.

[IMPORTANT]
====
It is recommended to use AAD to bind an encrypted value to application-specific context where possible, such as a user
identifier. This ensures that the context is authenticated when the value is later decrypted.

AAD should not contain confidential information.
====

Only the following Neo4j property types are supported as AAD:

* DATE
* INTEGER
* LOCAL TIME
* POINT
* STRING - consider normalizing values using something like `NFC` before providing them to the driver when both
encrypting and decrypting values
* ZONED TIME
* UUID
* BYTES


=== decrypt

The decrypting function `decrypt` functions similarly to `encrypt`

.Decrypt value
[source, javascript]
----
const decryptedValue = await driver.encryption.decrypt({
  ciphertext: record.get("accountBalance"), // <1>
  usePersistedAad: false, // <2>
  aad: "user1" // <2>
}) // <3>
----

<1> A mandatory parameter for providing the value to decrypt. This is expected to be `byte[]`.
<2> Parameters for selecting AAD handling. Either `usePersistedAad` must be true or `aad` must be set.
<3> Returns decrypted value.

The AAD step provides a choice of how AAD is handled. An external AAD can be provided using one of the `aad`
parameter. This AAD must be supplied independently during decryption and therefore can bind the encrypted value to
external application context, such as a user identifier.

Alternatively, `usePersistedAad` can be used to rely on the AAD configuration recorded in the encrypted value
metadata. If AAD was used when the value was encrypted, that AAD is used during decryption. If no AAD was used, no
effective AAD is used during decryption. Because this AAD is obtained from the encrypted value itself, it does not
bind the value to an independently supplied external context.

[IMPORTANT]
It is recommended to provide AAD externally when possible, especially when the encrypted value was bound to
application-specific context during encryption. The externally provided AAD must match the AAD used during encryption.


[#caching]
== Caching

The <<envelope-profile>> supports 2 related caches:

* <<key-cache>>
* <<key-alias-index>>

[NOTE]
Each profile instance maintains its own dedicated caches.

[#key-cache]
=== Key Cache

The driver caches decapsulated data encryption keys by default to avoid repeatedly resolving and decapsulating the same
key.

Depending on the <<key-encapsulation-service>> and <<encapsulated-key-record-repository>> implementations, resolving a
key may require network exchanges. Caching can therefore reduce the number of repeated key resolution operations.

The key cache is keyed by the key's globally unique identifier and has a configurable maximum size and time-to-live
(TTL). The default size is `100` and TTL is `15` minutes.

The key cache can be configured when creating an <<envelope-profile>>:

.Configure Key Cache
[source, javascript]
----
new EnvelopeEncryptionProfile({
    name: "main",
    encapsulationService: encapsulationService,
    keyRepository: new KeyRepo(),
    keyCacheTTL: 10 * 60 * 1000 // <1>
    keyCacheMaxSize: 10 // <2>
})
----

<1> Sets custom key cache TTL in milliseconds.
<2> Sets custom key cache Size.

The key cache is bounded and uses a least-recently-used (LRU) eviction policy when its configured maximum size is
reached. Entries that have exceeded their configured TTL are treated as cache misses and are not used.

The key cache can also be disabled by setting the max size to 0:

.Disable Key Cache
[source, javascript]
----
new EnvelopeEncryptionProfile({
    name: "main",
    encapsulationService: encapsulationService,
    keyRepository: new KeyRepo(),
    keyCacheMaxSize: 0 // <1>
})
----

<1> Disables key cache.

[#key-alias-index]
=== Key Alias Index

Aliases are resolved through a key alias index that maps aliases to key identifiers. The alias index does not contain
key material.

The alias index has its own configurable maximum size and TTL. The default size is `100` and TTL is `15` seconds.

[NOTE]
This allows alias mappings to expire independently of cached keys and limits the period for which a driver may use a
stale alias after it has been reassigned.

The alias index can be configured when creating an <<envelope-profile>>:

.Customize Key Alias Index
[source, javascript]
----
new EnvelopeEncryptionProfile({
        name: "main",
        encapsulationService: encapsService,
        keyRepository: new KeyRepo(),
        keyAliasIndexTTL: 10 * 1000 // <1>
        keyAliasIndexMaxSize: 10 // <2>
})
----

<1> Sets custom key alias index TTL in milliseconds.
<2> Sets custom key alias index size.

Like the key cache, the alias index is bounded and uses a least-recently-used (LRU) eviction policy when its configured
maximum size is reached. Entries that have exceeded their configured TTL are treated as cache misses and are not used.

The key alias index is disabled when the key cache is disabled. It can also be disabled independently:

.Disable Key Alias Index
[source, javascript]
----
new EnvelopeEncryptionProfile({
        name: "main",
        encapsulationService: encapsService,
        keyRepository: new KeyRepo(),
        keyAliasIndexMaxSize: 0 // <1>
})
----

<1> Disables key alias index.

[#fips-compliance]
== FIPS Compliance

FIPS compliant cryptography provider in Node

Encryption is performed using the WebCrypto API, when using node this API is called through the Node crypto implementation.

If you wish to ensure that the cryptographic provider used by the driver is FIPS compliant, 
you will need to ensure your JS runtime is correctly configured to use these providers. 
For node, this means following the (Node Crypto Fips Mode Guide)[https://nodejs.org/api/crypto.html#fips-mode].

[IMPORTANT]
====
The cryptographic algorithms and parameters used by this feature, including key sizes, initialization vector (IV) sizes,
and authentication tag sizes, have been selected with FIPS requirements in mind. However, FIPS compliance depends on
more than the algorithms and parameters used by the driver. It can also depend on the cryptographic provider or
validated cryptographic module, its configuration, the runtime environment, key management, storage, and other aspects
of the deployment that are outside the driver's control.

Users requiring FIPS-compliant operation are responsible for ensuring that the driver and its surrounding environment
are configured appropriately for their requirements.
====
